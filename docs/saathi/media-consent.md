# Media consent revisions

Schema9 extends the internal schema8 store with monotonic per-clip consent revisions and snapshots of each application transition. `consentRevision` and nullable `consentChangedAt` are metadata; `consentHistory(owner,id)` returns the owned revision/kind/flags/state/observation time. They are recorded data, not verified identity or a tamper-proof audit service.

New clips record `stored` at revision1. Processing revocation increments once when the flag actually changes. Deletion, storage revocation and explicit expiry purge record the first terminal transition atomically with BLOB/flag clearing. Repeating a transition or original admission cannot add another event, renew expiry, revive audio or regrant consent. No regrant method exists; a separately reviewed new admission is required. With the current revocation-only state machine there are at most three events per clip, bounded by existing lifetime record quotas.

Schema8 migration records `migrated_snapshot` of current flags/state at migration observation time. Older grant/revocation history and exact last-change time are unknown, so `consentChangedAt` stays null until a new recorded transition. Migration preserves bytes, deadline, request digest and terminal state. It never treats original clip creation as proof of historical processing consent. Tests build the real old schema before upgrading and check this distinction.

`checkProcessingConsent(owner,id,expectedRevision)` checks a consistent read snapshot: owned clip, active session/storage, unexpired nonterminal media, exact current revision and processing consent. It returns clip ID/revision/content digest/check time/deadline; no audio or grant token. Foreign owner gets404, expired/terminal media410, stale revision409 and current-but-missing processing consent403. This check alone cannot authorize later inference; a future durable admission/start operation must recheck authoritative consent and pin request/media/provider-role identity.

No processing lease, attempts/spend ledger, provider invocation, cancellation bus, route or scheduler is implemented here. A revoke can prevent future checks; it cannot recall bytes already returned or sent. Public speech stays disabled until processing admission/revocation/restart semantics, budgets and actual consented provider evaluation are ready. Only fresh synthetic databases were migrated in development; do not start schema9 code against existing profiles or deploy without a separately authorized consistent backup/upgrade. Older schema7/8 binaries refuse9.

Transition and history writes share SQLite transactions, including explicit expiry cleanup. Failure to write history rolls back flags, BLOB changes or new admission. Tests inject history failures and retain the separate-process duplicate/quota checks. The implementation uses [SQLite transaction isolation](https://www.sqlite.org/isolation.html) through the existing [Bun SQLite API](https://bun.sh/docs/runtime/sqlite); it adds no dependency or remote storage.
