# Native read-only plan execution

The read-step core extends saved structured proposals with one explicit local execution batch. It supports only `demo.clinic.options` and `handoff.manual`. It never calls a model, creates or approves a booking, sends a message, pays a bill or issues a receipt. General autonomous planning/replanning and remote integrations are still incomplete. Browser controls for this path follow separately; consult HANDOFF for actual source/public status.

After an owned plan is `DRAFT_READY`, POST an empty JSON object to `/api/task-plans/:id/run-readonly` using the existing same-origin session and CSRF header. The server revalidates its fixed tool/risk/date contract and runs at most three local steps in plan order. Clients cannot supply tools, altered arguments or approvals in this request. Another owner gets404. A non-ready/cancelled draft cannot start a new read. No configured inference key or new inference allowance is consumed by this batch.

Results appear as `read_result` on the owned plan. They have `mode:read_only`, a saved retrieval timestamp and per-step typed outcomes/evidence modes. A completed lookup means a controlled SQL mock was read, not that the user's wider goal or a real appointment was fulfilled. Slot prices/labels remain mock. Manual instructions are unverified draft text and yield `requires_user_action`; dependent steps are skipped. Native output schema violations yield `permanently_failed` without saving forged live/reference fields. Empty/unavailable dates remain explicitly unavailable.

Each plan can have one committed read result. Duplicate posts return the exact saved observations and original time rather than silently refreshing availability. Cancellation after a read does not undo the read; its saved evidence is still accessible, and repeated posts return that evidence without executing again. To obtain new evidence, create/review a new dated proposal. There is no automatic retry or poll.

Schema v7 adds only `plan_read_runs`, retaining v6 task pins, drafts/events and all earlier state. The read batch and observation save use one SQLite transaction; unexpected failures roll back partial observations. All current tools are bounded synchronous local reads/drafts, so this does not leave an external side effect in doubt. One-second step timing is checked after the local call; it is not a hard process interrupt. Persisted observations survive reopen; startup never invokes read tools. Old binaries cannot open v7 and must not be forced by falsifying schema versions. Public upgrades still need the retained-disk backup/release procedure.

The executor's clinic interface contains only an `options(date)` read method. Future authenticated/remote/async tools need explicit grants, deadlines, per-operation durability/reconciliation and genuine provider evidence; they cannot inherit authority from model JSON or this local transaction. No broad MCP/write engine is claimed.

Tests cover explicit owner/CSRF/empty-input gates, readiness/cancel boundaries, duplicate/original-time persistence and real reopen, manual prerequisites, zero booking/extra inference effects, v6 migration, rejected fake-live output and atomic rollback. CI uses synthetic state and no provider keys. Next is the review-panel control/evidence display and browser/packed acceptance, then a separately backed-up public release when ready.
